# watch-engine 模块需求说明

## 1. 文档目的

本文定义 `watch-engine` 作为独立、通用、可复用功能模块的目标、使用者、能力边界、功能需求、非功能需求和 v0.1 验收标准。

本文回答“为什么需要这个模块、它应当提供什么能力”。整体技术结构见 [架构设计](architecture.zh-CN.md)，当前版本的代码、数据、配置、测试和发布落地见 [实际落地技术方案](implementation.zh-CN.md)，下游接入步骤见 [采用指南](adoption-guide.zh-CN.md)。

## 2. 模块定位

`watch-engine` 是一个可独立安装、运行、测试和版本化的 Python Condition Watch Runtime。

它为持续监视类程序提供与业务领域无关的可靠运行能力：

- 按时间或外部信号触发观测；
- 保存原始观测证据及执行诊断信息；
- 区分有效、降级和失败观测；
- 维护最后一份可信的 Authority（权威状态）；
- 调用下游提供的领域策略解释状态转换；
- 原子地产生持久事件；
- 通过事务型 Outbox 可靠投递事件；
- 在失败、重试和进程重启后保持一致行为。

它可以被其他功能模块、其他工程或其他开发者的程序采用。通用库存监控、服务健康检查、文件状态监控和自动化条件监视都只是可能的下游场景，不属于引擎核心。

## 3. 独立性与复用目标

模块必须满足：

1. **独立安装**：下游可作为 Python 包安装，不需要复制源码或修改引擎内部文件。
2. **独立运行**：除公开依赖外，不依赖特定厂商、特定通知渠道或某个业务仓库。
3. **独立测试**：核心测试不需要真实网站、真实通知服务或下游工程。
4. **独立版本化**：采用 Semantic Versioning，公开接口和跨工程契约的变更可被识别。
5. **低成本采用**：下游只需实现领域边界接口并完成组合装配。
6. **稳定契约**：下游依赖 Public API 和公开 Schema，不依赖 SQLite 表结构或内部类。
7. **可替换边界**：抓取、解析、领域状态解释和通知发送由下游实现。
8. **独立价值**：即使当前所有下游工程停止存在，本模块仍可供新的监视程序使用。

## 4. 目标使用者

- 需要构建周期性或事件触发式监视程序的开发者；
- 需要可靠状态转换和通知投递能力的功能模块；
- 希望复用统一 Observation、Authority、Event 流水线的自动化系统；
- 需要将“观测失败”与“目标状态变化”严格分离的工程。

## 5. 典型使用场景

### 5.1 商品或资源可用性监控

下游负责访问页面/API并解析库存；引擎负责调度、可信状态、变化事件和可靠投递。

### 5.2 服务健康与依赖状态监控

下游采集服务证据并定义健康状态；引擎防止暂时观测失败被误判为服务状态变化。

### 5.3 本地文件、任务或构建结果监控

下游提供文件或任务观察器；引擎记录证据并在有效状态转换时产生事件。

### 5.4 Agent / Code Driver 条件监视

下游定义目标条件、证据和转移策略；引擎提供可恢复的观察与事件机制，不理解 Agent 的领域语义。

## 6. 核心概念

- **WatchDefinition**：以稳定 `watch_id` 组合 Trigger、Observer、TransitionPolicy 和重试配置。
- **Trigger**：决定一次运行何时可以开始。
- **Observer**：取得领域证据并返回 Observation。
- **Observation**：一次不可变观测，质量为 `VALID`、`DEGRADED` 或 `FAILED`。
- **Authority**：某个 Watch 当前最新且可信的 `VALID` Observation。
- **TransitionPolicy**：由下游提供的纯领域决策逻辑，比较前后 Authority 并创建 EventDraft。
- **WatchEvent**：由引擎分配稳定身份并持久化的事件信封。
- **Outbox**：与 Authority 提升和事件创建保持事务一致的待投递记录。
- **EventSink**：下游提供的投递边界，按 `event_id` 实现幂等。

## 7. 功能需求

### FR-01 Watch 定义

- 每个 Watch 必须拥有稳定、非空的 `watch_id`。
- 引擎必须允许不同 Watch 使用不同的 Trigger、Observer、TransitionPolicy 和重试配置。
- 领域配置不得被写死在引擎内部。

### FR-02 触发

v0.1 必须支持：

- 带可选抖动的 Interval Trigger；
- 显式时区的 Cron Trigger；
- 进程内 Manual Trigger。

Trigger 只决定运行时机，不负责取得或解释领域状态。

### FR-03 观测与分类

- Observer 必须返回带时区的 `observed_at`。
- 有效证据返回 `VALID`。
- 可诊断但不足以更新可信状态的证据返回 `DEGRADED`。
- 无法取得或解释证据时返回/形成 `FAILED`。
- 所有完成的 Observation 必须持久保存用于诊断。

### FR-04 Observer 重试

- Observer 抛出异常时，引擎按 Watch 的有界策略重试。
- 重试耗尽后必须保存 `FAILED` Observation。
- Observer 主动返回 `DEGRADED` 或 `FAILED` 时不得隐式重试。

### FR-05 Authority 维护

- 只有未过时的 `VALID` Observation 可以成为 Authority。
- `DEGRADED` 和 `FAILED` 不得覆盖 Authority。
- 时间早于或等于现有 Authority 的 Observation 只作为证据保存，不触发 Policy，不产生事件。
- 首次有效观测是否产生事件由下游 Policy 决定。

### FR-06 状态转换

- 引擎必须把 Previous Authority 和 Current Observation 交给 TransitionPolicy。
- Policy 可以返回零个或多个 EventDraft。
- Policy 必须是快速、确定性的纯领域决策，不执行网络或阻塞 I/O，不产生数据库外副作用。

### FR-07 原子持久化

对于一次有效提升，以下变化必须位于同一事务：

- Policy 决策；
- Authority 更新；
- WatchEvent 创建；
- Outbox 创建。

任一环节失败时，上述变化必须整体回滚；已经保存的 Observation 仍应保留用于诊断。

### FR-08 事件与去重

- 每次真实事件发生必须获得新的 `event_id`。
- 相同领域转换以后再次发生时仍是新事件。
- `dedupe_key` 用于领域关联，不作为全局唯一事件身份。
- 投递重试必须复用同一持久事件及其 `event_id`。

### FR-09 可靠投递

- 投递语义为 at-least-once。
- 失败投递采用有界指数退避。
- 重启后必须继续处理未完成投递。
- 重试耗尽的记录进入 `DEAD`，不得被静默删除。
- EventSink 必须按 `event_id` 幂等。

### FR-10 跨工程事件契约

- 跨工程事件格式由 `schemas/watch-event-v1.json` 定义。
- 下游不得通过读取内部数据库表代替公开事件契约。
- 破坏性 Schema 变更必须发布新的契约版本。

### FR-11 数据生命周期

- 每个 JSON 字段编码后不得超过 1 MiB，错误字段不得超过 2,048 字符；
- 自动捕获的异常只保存异常类型，不保存可能含秘密或个人信息的异常消息；
- 清理操作不得删除当前 Authority 或未完成投递；
- 删除整个 Watch 时，若仍有未投递事件必须默认拒绝，并要求显式破坏性确认；
- POSIX 下 SQLite 数据库及 WAL/SHM 文件权限必须为 `0600`，数据库路径不得为符号链接。
- v0.1 的 Store 必须使用文件数据库；不支持会在多连接间丢失 Schema 的 `:memory:` 路径，并应 fail-fast。
- 引擎自身日志不得输出调用方可控的 Watch/Event 标识、载荷或异常消息。

## 8. 非功能需求

### NFR-01 正确性

暂时观测失败不得被解释为领域状态变化；Authority、Event 与 Outbox 的一致性优先于吞吐量。

### NFR-02 可恢复性

进程退出、Observer 异常和 EventSink 失败后，已提交证据和事件状态必须可恢复。

### NFR-03 可诊断性

运行记录、Observation、异常类型、尝试次数、投递尝试和 `DEAD` 状态必须可查询。

### NFR-04 可移植性

支持 Python 3.11+；v0.1 使用 SQLite 提供单节点持久化，不要求 Redis、Kafka 或 PostgreSQL。

### NFR-05 可测试性

核心测试必须在无网络、无真实第三方服务条件下执行，并覆盖事务、乱序、失败和重启语义。

### NFR-06 兼容性

- Public API 和事件 Schema 是正式兼容性边界。
- 内部模块、私有类型和 SQLite 表结构不承诺兼容。
- 版本遵循 Semantic Versioning。

### NFR-07 安全性

引擎字段不得包含账号密码、Token、个人信息等敏感数据；自动捕获的异常消息必须脱敏，秘密的加载和保管由下游程序负责。部署方必须定义保留期限并调用公开清理 API。

## 9. 明确不负责的内容

v0.1 不负责：

- 抓取网站、调用特定业务 API 或解析业务页面；
- 理解 `AVAILABLE`、`HEALTHY` 等领域状态；
- 直接支持微信、邮件、Slack 等特定通知服务商；
- Web 管理后台；
- 分布式调度、分布式锁和多节点一致性；
- 动态插件市场；
- 进程监督和操作系统服务管理；
- 下游业务配置与秘密管理。

这些能力应位于下游模块、通知网关或未来明确版本中。

## 10. v0.1 完整采用验收标准

`v0.1.0` 已于 2026-08-10 发布。以下条件用于判断后续维护版本是否完成“代码发布之后的真实独立采用闭环”，
而不是倒置为一个尚未发生的 Release 门槛：

1. 核心能力通过自动化测试，且测试不依赖网络。
2. Python 3.11、3.12、3.13 的 CI 通过。
3. Public API 有最小可运行示例。
4. `watch-event-v1` Schema 可被下游独立校验。
5. 失败观测不会覆盖 Authority。
6. 乱序/同时间戳观测不会重复提升或产生事件。
7. Authority、Event、Outbox 具备原子一致性。
8. 投递失败可重试、可跨重启恢复，并最终进入 `DEAD`。
9. 至少一个独立下游工程完成端到端采用验证。
10. 模块需求、架构设计、实际落地技术方案和采用指南与实现一致。

核心测试、CI、Tag、Release 与首个独立下游端到端采用均已完成；采用证据保存在下游私有运维记录中，公开仓库只记录匿名结论，不披露仓库名称、业务目标或部署信息。

## 11. 独立采用验证

一个独立下游已经完成真实采用，用于验证模块契约和采用成本；其领域逻辑不得反向写入 `watch-engine`。

验证链路：

`Domain Observer → Observation → Authority → TransitionPolicy → WatchEvent → EventSink`

发现的通用缺口可以回到本模块修复；仅属于特定业务的行为必须保留在下游工程。

## 12. 后续演进原则

未来能力只有同时满足以下条件才应进入核心：

- 能被多个独立下游复用；
- 属于可靠监视运行时的职责；
- 不迫使现有下游绑定某个业务领域或基础设施；
- 可以形成稳定、可测试、可版本化的接口；
- 带来的复杂度与真实采用需求相匹配。

不得为了扩大功能列表而提前引入分布式协调、消息代理、管理后台或动态插件系统。
